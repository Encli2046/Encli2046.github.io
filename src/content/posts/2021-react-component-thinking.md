刚开始接触 React 的时候，我最不适应的是它把页面拆成很多组件。以前写页面，HTML、CSS、JavaScript 分开看，哪里需要效果就去哪里补一点。React 让这些东西围绕组件组织起来，一开始反而让我觉得麻烦。

![React 组件](/images/posts/personal-growth/2021-react-component-thinking.jpg)

真正写了一段时间以后，我才慢慢理解组件化的好处。一个按钮不只是一个标签，它有状态，有样式，有点击后的行为。一个列表也不只是一堆重复结构，它可以接收数据，然后按同一种方式展示。页面被拆开以后，每一块都更容易理解。

React 也让我重新看待数据流。以前我经常直接改页面，哪里显示不对就去操作哪里。React 更强调由状态驱动界面：数据变了，界面自然跟着变。这个想法刚开始有点绕，但熟悉以后会发现它让很多逻辑变得更清楚。

当然，学习过程也没那么顺。props 和 state 的边界、组件拆分的粒度、什么时候该抽函数，什么时候只是过度设计，这些都需要在实际项目里慢慢摸索。我也写过很多不必要的组件，把简单问题弄复杂。

2021 年的 React 学习给我最大的影响，不是掌握了某个框架，而是改变了我看页面的方式。以前看到的是一个整体页面，现在会先想它由哪些部分组成，哪些数据会变化，哪些东西应该复用。

这种思维后来不只用在 React 里。做其他项目时，我也会自然地把复杂问题拆成小块。组件化本质上是一种整理能力：把混在一起的东西分开，让每一部分都有清楚的责任。

## 我学到的组件拆分原则

后来我给自己定了一个很朴素的原则：如果一段界面有独立含义、独立状态或会被复用，就可以考虑拆成组件；如果只是为了“看起来更工程化”而拆，反而会增加理解成本。组件不是越小越好，而是边界要自然。

我也逐渐重视组件的输入输出。一个组件接收什么数据，触发什么事件，内部保留什么状态，这些关系越清楚，整个页面越容易维护。很多 React 代码难读，不是因为 JSX 复杂，而是数据流方向不清楚。

## 状态管理给我的提醒

React 让我明白，界面问题常常不是样式问题，而是状态问题。哪个状态属于当前组件，哪个状态应该上提，哪个状态可以通过计算得到，这些判断会直接影响代码结构。

我曾经把很多可以计算的值都放进状态里，结果需要到处同步，越写越乱。后来才知道，能从已有数据推导出来的东西，最好不要再存一份。这个小原则听起来简单，却能避免很多隐蔽错误。
